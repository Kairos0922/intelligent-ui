# P0-1 反证实验：预登记判决规则

> 本文件在写任何实验代码之前创建，用于防止事后调整通过标准。
> 创建时间：2026-11-02（实验开始前）
> 依据：`INTELLIGENT-UI-PLAN.md` §8.2 P0-1、§8.5 第 1 项

## 要反证的中心假设

> “宿主真正缺的是可抄的样例 + 数据接入，不是协议契约。”
>
> 如果这个竞争解释成立，那么用现有 `registerBlock` 就能做出可用的登机牌，
> 不需要先补 action lifecycle / data envelope / storage / pass 协议。

## 实验范围（只做这些）

1. 用公开 `registerBlock` API 写一个 `pass` 自定义块，**不修改 core / protocol / validator**。
2. 接半真实数据：本地 issuer feed fixture，包含一次登机口变更（D7 → D2）与一次撤销。
3. 跑通三条路径：
   - **打开**：宿主渲染结论 + pass + 解释；
   - **出示**：点主行动打开可扫描二维码（用真实 QR 编码，并用解码器验证）；
   - **离线再打开**：断网、刷新页面，从宿主快照恢复 pass，显示离线/过期语义。
4. 记录每个卡点：出现在哪一层、用了多少变通代码、是否必须改协议才能消除。

## 判决规则（先写死）

实验结束后，按以下顺序判定：

### A. “契约不是瓶颈”成立（改走样例 + recipe 文档）

同时满足：

- 三条路径全部跑通；
- 卡点总数 **< 3**；
- 没有卡点落在 action 状态、持久化状态、证据/新鲜度这三类；
- 不修改 core 即可让模型稳定产出该 artifact。

→ 结论：优先补 `pass` 样例、recipe 文档、数据接入指南。

### B. “契约是瓶颈”成立（继续 Protocol Spec）

满足任一：

- 三条路径中有一条必须改 core/protocol 才能可靠跑通；
- 卡点总数 **≥ 3**，且至少两类落在 action / state / provenance；
- 模型可以产出“看起来有效”的 pass，但 SDK 无法区分 `integrity` 与 `freshness`，也无法阻止伪造的 `verified`。

→ 结论：卡点清单直接转为 Protocol Spec 的验收用例；按 §8.5 第 2–6 项修订方案。

### C. 证据不足（不得下结论）

- 实验环境不是真实宿主，或
- 半真实数据无法代表真实 issuer，或
- 二维码/离线路径因环境限制未真正验证。

→ 结论：只记录证据缺口，不把实验当作产品结论；补做真实宿主实验后再判。

## 判定时必须回答

| 问题 | 记录方式 |
|---|---|
| 卡点在哪一层？（块 / 宿主 / 协议 / 数据） | 每条一行，标层 |
| 绕过去需要多少代码？ | 行数或“改 core 的哪个文件” |
| 换一个宿主是否要重写？ | 是/否 + 原因 |
| 模型能否伪造通过状态？ | 能/不能 + 复现步骤 |
| 离线时“可出示”是否仍成立？ | 是/否 + 判定函数 |

## 非目标

- 不证明二维码可被机场闸机扫描（只证明编码可被标准解码器读出）。
- 不证明 issuer 签名真实（fixture 中的签名是占位符）。
- 不把本实验当作可用产品、无障碍审计或安全审计。
